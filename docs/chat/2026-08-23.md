## 07:33:11Z — ImageToolbox saving + full non-destructive editor

### User

> Plus we can take the image saving code from imagetoolbox and incorporate it into aves and make it a full non destructive editor

### Decision

Make the Aves fork a genuine non-destructive editor, not merely a gallery with a few filters.

Architectural direction:

- Aves remains the gallery/viewer/editor-shell foundation.
- ImageToolbox is used as a source/reference for robust Android save/export abstractions and, where appropriate, Apache-2.0-compatible adapted code.
- Because Aves is Flutter/Dart and ImageToolbox is native Kotlin/Android, do not assume direct copy/paste integration.
- Separate preview/edit processing from export/storage.
- Keep source media untouched during editing.
- Store edit state as a persistent recipe/stack.
- Explicit export renders the stack and creates a new output unless the user explicitly selects an overwrite behavior later.

Desired non-destructive capabilities discussed:

- persistent edit history;
- operation enable/disable;
- operation reorder/duplicate/reset/delete;
- hold-to-preview original;
- split-screen original/edited comparison later;
- reusable edit recipes/presets;
- internal edit database plus optional portable sidecar later;
- high-quality export profiles;
- preserve metadata/color profile as policy permits;
- avoid repeated decode/re-encode cycles.

ImageToolbox architecture found during inspection:

- `ImageCompressor` separates compression/render output from saving;
- `ImageSaveTarget` carries source URI, output bytes, metadata, format, MIME type, extension, filename/preset data;
- `FileController` handles save/move, metadata, output destinations and file transfer;
- `AndroidFileController` contains destination selection, overwrite/new-copy behavior, one-time save locations, save-to-original-folder behavior, metadata handling and media scanning.

Aves already has useful native infrastructure:

- `MediaEditService` and Android `MediaEditHandler`;
- existing provider/storage abstractions;
- editor shell with `ImageEditorPage`;
- top-level editor currently exposes only `transform` upstream;
- Save Copy button exists in upstream editor UI but its editor handler is empty.

## 07:50:04Z — Ultra HDR support

### User

> And how hard is it to add ultraHDR support

### Decision

Ultra HDR is a high-priority feature and should be implemented in stages.

Desired stages:

1. detect/display Ultra HDR correctly;
2. preserve gain maps through crop/rotate/scale where platform APIs support it;
3. make color/tonal processing Ultra-HDR-aware;
4. regenerate an appropriate gain map after arbitrary edits;
5. export JPEG/R Ultra HDR;
6. investigate HEIC Ultra HDR support on Android 16/API 36 later.

Important correctness rule:

Do **not** simply edit the SDR base image and blindly reuse the original gain map after strong tonal/color changes. Advanced edits can invalidate the relationship between SDR base and HDR rendition.

Long-term conceptual pipeline:

`Ultra HDR source -> HDR/high-precision representation -> edit graph -> derive SDR rendition + regenerated gain map -> Ultra HDR output`
